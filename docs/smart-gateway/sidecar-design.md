# 反代网关外置 sidecar（方案 B）设计

状态：仅设计，未实现。当前仍是方案 A（反代网关随主程序同进程运行）。本文只记录将来拆分时的边界，避免到时重新讨论。

## 为什么可能要拆

- AG / Kiro 反代的崩溃、内存增长、长连接不应拖垮主程序与智能网关。
- 反代可以独立升级、独立重启，不需要重启整个桌面端。
- 其他客户端（自定义 Agent）想直接使用反代，不必装整套桌面端。

不拆的理由（当前选择方案 A）：进程管理、账号文件并发、升级与回滚都会变复杂，而收益目前不足以抵消。

## 进程边界

| 项 | 方案 A（现状） | 方案 B（目标） |
| --- | --- | --- |
| 进程 | 主程序内的 tokio 任务 | 独立可执行文件，主程序负责启停与健康检查 |
| 监听 | `127.0.0.1:15830`（AG）、`127.0.0.1:15831`（Kiro） | 端口不变，仍只听 `127.0.0.1` |
| 鉴权 | 本机、无额外 Key | 启动时生成一次性 Key，主程序与 sidecar 共享；请求必须带 Key |
| 与智能网关关系 | `up_ag_15830` / `up_kiro_15831` 上游 | 不变：主程序只把它当普通上游，不进上游池之外的特殊路径 |

端口、上游 id、`provider_kind`、用量 hop（`antigravity` / `kiro` 优先于 `smart_gateway`）都不变，所以智能网关、目录、用量统计不需要改。

## 数据与账号

- 账号文件保持现有位置：AG 账号存储与 `~/.claude-switcher/kiro_accounts.json`，`kiro_models.json`。
- 同一时刻只能有一个进程写账号文件：切到 sidecar 后，主程序只读，所有刷新令牌、冷却标记、账号轮换由 sidecar 完成；主程序通过 sidecar 的本地管理接口读取账号状态并发起登录。
- 登录流程（设备码、Social PKCE 回调、粘贴回调地址）由 sidecar 承载回调端口，主程序负责打开浏览器与展示结果。
- `thought-signatures.db` 仍是独立文件，只由 sidecar 访问。
- 主库 Schema、ZIP / WebDAV 备份范围不变；账号文件是否进备份保持现状。

## 用量与日志

- sidecar 继续写 `proxy_request_logs`：用只写连接入同一个 SQLite（WAL），或经主程序的本地写入接口转存；二选一，实现时再定。
- `correlation_id` 与 `x-aisw-request-id` / `x-aisw-target-app` 透传规则不变，避免双计。

## 生命周期

1. 主程序启动：检查 `local_gateway_enabled`，开启时拉起 sidecar，等待健康检查（`/healthz`）通过后再标记上游可用。
2. sidecar 崩溃：主程序按退避重启；重启期间上游返回 504，不触发跨供应商 failover（与现有 AG/Kiro 行为一致）。
3. 主程序退出：先优雅停 sidecar；异常退出时 sidecar 通过父进程存活检查自行退出，避免端口被占。
4. 开机自启只登记主程序，不单独登记 sidecar。

## 升级与回滚

- sidecar 与主程序同版本打包，主程序启动时校验 sidecar 版本，不匹配则拒绝拉起并提示。
- 回滚到方案 A 只需把 `local_gateway_enabled` 的运行方式切回进程内实现；账号文件格式不变，所以无需迁移。
- 先保留进程内实现一个大版本，再删除。

## 迁移步骤（将来）

1. 把 `antigravity/gateway` 与 `kiro/gateway` 提成独立 crate，主程序与 sidecar 共用。
2. 给 sidecar 增加最小管理接口：状态、账号列表、登录、刷新模型。
3. 主程序加“进程内 / 外置”开关，默认进程内。
4. L1 / L2 增加两种运行方式的同一套场景。
5. 稳定一个版本后再决定是否默认外置。

## 不做

- 不监听局域网。
- 不引入 Windows 服务或开机服务。
- 不为 sidecar 新增对外端口。
